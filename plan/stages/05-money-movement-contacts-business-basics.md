# Stage 5: Money movement + contacts + business basics

Purpose: a stage of the Kawase build. Source of truth for scope is `plan/MASTER-PLAN.md`; decisions are in `context/08-product-research/DECISIONS-FROM-ABU.md`.
Status: not started

## Scope (from the master plan)
- Send, receive (QR, share link), request money and split bills (C3), batch payouts (Multicall3From), memo, crosschain send; the approval endpoint (lock, fresh evaluate, spend reservation, then the allowance redeem or a wallet signature); post-verification against the draft; `tx_attempts` + reconciliation; the money-ending taxonomy.
- `apps/chain-watcher` (system emitter + ERC-20 + Memo, with cursors) → incoming-payment matching + inbox.
- Contacts: versioned addresses, per-network trust, verification method, 24 h change cooldown + hold, first-time and lookalike warnings, ENS/Basenames/ArcNS ("unofficial"), QR scan, save-from-received.
- Limits (per-tx, daily, weekly, allowlist, new-recipient cooldown, temporary raise with auto-restore, pause-all).
- Business basics (R): business profile, invoices = payment requests with memo matching, vendor labels on contacts.
- Deploy `executor` (reconcile, track-intent) + `chain-watcher`.
- **Exit:** a real send on testnet **and** mainnet (small amount) with receipts; an incoming payment detected; an address change freezes payments; duplicate taps never double-send.

## Build order (decided 2026-10-01, Claude; Abu: "lets continue building")
The Phase D send / request / contacts screens were never built, and `policy`, `intents` and `cards` were still empty packages, so the stage starts from the data and the rules and ends at the screens.
- **5a — Send with real execution.**
  1. Tables (migration `0005`): `contacts`, `contact_addresses` (versioned, `pending_cooldown` → `active`), `contact_address_trust` (per network), `contact_address_events`, `intents`, `intent_drafts`, `approvals`, `spend_ledger`; all in the guest-merge list.
  2. `packages/policy`: pure `evaluateSend()` with the five kinds, the reason enum and the route (`allowance` | `wallet_signature`); the remaining allowance is read **from the chain** (`ERC20PeriodTransferEnforcer.getAvailableAmount`), not estimated.
  3. `packages/intents`: the A2A state machine, `SendDraft` + its EIP-712 hash (ARCHITECTURE §4), the money-ending taxonomy.
  4. Api: recipients (`@handle` → that user's wallet, contacts by name or alias, a pasted `0x` address; lookalike and first-time checks), contacts CRUD with the 24 h address-change hold, and intents (`draft`, `get`, `cancel`, `approve`, `submit`). Approve = row lock + per-(user, network) advisory lock → version check → fresh `evaluate` → `spend_ledger` reservation → `tx_attempts(prepared)` with a v4 key **persisted before** Circle is called → route `allowance`: the ops DCW redeems the user's delegation (`refId = intentId:vN`); route `wallet_signature`: an unsigned USDC transfer the device signs, checked against the draft before broadcast. Completion only on a witness: the receipt's `Transfer` log must equal the draft.
  5. Tracking: a reconcile function (Circle state by transaction id / idempotency key, receipts by hash) that runs after approve, on read of a non-final intent, and on a sweep timer inside the api. **Moving this into the DBOS executor is deferred to Stage 8**, when automations need workflows anyway; nothing in the guarantees changes (key persisted first, no auto-retry of an unknown outcome, reconcile decides).
  6. Agent: `find_recipient`, `propose_send` (the model passes the words the person used; code resolves and checks); the send card in chat with the resolve-and-resume fixes inline (unknown name → add-contact sheet → the same intent re-drafts; asset chips; policy refusal with the numbers and no split).
  7. App: `/send` (recipient → amount + note → review with trust chip, first-time / lookalike rows and the allowance meter → sending → receipt), contacts (list, add sheet, detail with address versions), the fan's Send, Activity rows named from contacts; `send` and `contacts` added to `SHIPPED_CAPABILITIES`.
- **5b — Request and incoming.** `payment_requests` + the share card + `/r/[token]` (a pre-filled send for the payer); `apps/chain-watcher` (system emitter + ERC-20, cursors) → incoming-payment matching → inbox items; save a contact from a received payment.
- **5c — Limits and business.** Limits UI (per-tx, daily, weekly, temporary raise with auto-restore, pause-all, new-recipient cooldown), batch payouts (Multicall3From) and split bills, QR scan (`expo-camera`), device-contact import (`expo-contacts`), names (ENS/Basenames, "unofficial"), business profile + invoices + vendor labels; web parity and deploy.
- **Memo (C5):** Arc's Memo contract only accepts a direct EOA call and its data is public (`context/01-arc/gotchas.md` #27, #29), and the allowance can only call USDC `transfer`. So a note on a send is a private note stored with the intent and shown on the receipt; the on-chain memo is used for payment requests in 5b (a request id, never personal text).
