## 2. RTL (Arabic)
- Expo: "RTL support is enabled by default. Layout direction follows React Native's `I18nManager`"; `supportsRTL: false` / `forcesRTL: true` via the `expo-localization` config plugin [VERIFIED, Expo guide].
- `I18nManager.allowRTL()` and `forceRTL()`: "Changes take effect on the next application start, not immediately"; `forceRTL` is "Only meant for development and testing". `swapLeftAndRightInRTL()` needs no restart [VERIFIED, https://reactnative.dev/docs/i18nmanager].
- Consequence: switching the in-app language **to or from Arabic on native requires an app reload** (e.g., `expo-updates` `reloadAsync` or asking the user to restart) [INFERENCE from the above]. On web, set `dir="rtl"` on `<html>` [INFERENCE].
- Use logical styles (`start`/`end`, `marginStart`) rather than `left`/`right` [INFERENCE].

## 3. Numbers and money
- Hermes supports `Intl.NumberFormat`, `Intl.DateTimeFormat`, `Intl.Collator`, using platform facilities, "resulting in some variance in behaviours across Android and iOS"; iOS lacks `notation: 'compact'` and `signDisplay`; `formatToParts` is Android-only; PluralRules/RelativeTimeFormat/ListFormat are not listed [VERIFIED, Hermes IntlAPIs.md]. This doc may lag current Hermes; test on device [INFERENCE].
- `Intl.NumberFormat` `style: "currency"` accepts only well-formed ISO 4217-style codes [VERIFIED, MDN]. Local test: `currency: "USDC"` throws `RangeError: Invalid currency code : USDC` [VERIFIED, `intl-numberformat-test.txt`]. **Stablecoins must be formatted as decimals + a unit suffix/prefix, not as Intl currency** (e.g., fr-FR `1 234,123456 USDC`) [VERIFIED output; approach INFERENCE].
- Locale differences that matter for money confirmation [VERIFIED, `intl-numberformat-test.txt`]:
  - `ar-EG` renders Arabic-Indic digits: `‏١٬٢٣٤٫٥٠ US$`.
  - `fr-FR` uses a narrow no-break space group separator and comma decimal: `1 234,50 $US`.
  - `es-ES` omits grouping at 4 digits: `1234,50 US$`.
  - Nigerian locales `en-NG`, `yo-NG`, `ha-NG`, `ig-NG`, `pcm-NG` resolve in ICU 78 and format NGN as `₦1,234.50` (Hausa with a space).
- Rules [INFERENCE]: keep amounts as integer base units / decimal strings, never floats; format only at display; the confirmation sheet should also show the canonical Latin-digit amount and the token symbol, so a user in `ar` or `fr` cannot misread `1,234` vs `1.234`.
- Parsing user-typed amounts must be locale-aware (comma vs dot decimal) and echoed back before any write [INFERENCE].

## 4. Agent replies in the user's language
- Anthropic: "for production applications you should state the target language explicitly. The most reliable place to do this is the system prompt"; "If your application lets users pick a language at runtime, interpolate that choice into the system prompt rather than relying on Claude to infer it" [VERIFIED, https://platform.claude.com/docs/en/build-with-claude/multilingual-support].
- Anthropic's published relative-to-English scores (Sonnet 4.5 / Haiku 4.5, with extended thinking): French 97.5% / 95.7%, Spanish 98.2% / 96.4%, Portuguese (BR) 97.8% / 96.1%, Arabic 97.2% / 92.5%, Chinese (Simplified) 96.9% / 94.2%, **Yoruba 79.7% / 52.7%**. Hausa, Igbo and Nigerian Pidgin are not listed [VERIFIED, same]. (Model-choice details live in `llm-choice.md`.)
- Pattern [INFERENCE]:
  1. Store `uiLocale` (e.g., `fr-FR`) and optional `replyLanguage` per user.
  2. System prompt: "Respond in {language name}. Keep token symbols, addresses, chain names and numbers exactly as provided by tools."
  3. Tools return raw values; **UI components format them with the device locale**, not the model. The model never re-types an amount inside prose for a write.
  4. Static UI strings come from i18next/Lingui catalogs; generative card labels use the same catalog keys (json-render has a `$t` directive, `json-render-README.md:147`) so cards switch language with the app.
  5. For Yoruba/Hausa/Igbo/Pidgin, show a "beta" badge and fall back to English for confirmations until tested [INFERENCE; justified by the 79.7%/52.7% Yoruba figures].

## 5. Recommendation [INFERENCE]
- **i18next + react-i18next** on both Expo and web (one codebase, runtime `changeLanguage`, no Babel macro step), with `expo-localization` for the initial locale and `@formatjs/intl-pluralrules` (+ `intl-locale`) polyfills on Hermes. Lingui is an equally valid choice if we want compile-time extraction; avoid `next-intl` unless the web app is Next.js-only and we accept two i18n stacks.
- A single `formatAmount(baseUnits, decimals, symbol, locale)` helper shared by web and native.
- Launch languages: en, fr, es, pt, ar (RTL), zh; Nigerian languages behind a beta flag pending voice/LLM tests (see `language-coverage-matrix.md`).
