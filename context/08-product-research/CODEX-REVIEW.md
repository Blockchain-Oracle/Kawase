# Independent review of the Arc agent product research

Purpose: review the existing research against Abu's words, check the architecture-bearing claims independently, and give a decision-ready direction before implementation planning.
Sources: Abu's verbatim brief; the files under `context/08-product-research/`; `context/00-hackathon/judging-and-submission.md`; the primary URLs and read-only commands below.
Reviewed: 2026-09-29. **No transaction, account creation, credential use, or funded runtime test was performed.**

## Executive judgment [OPINION]

The research is unusually useful as an inventory and evidence map. It captures the main vision and correctly identifies **unattended signing authority** as the hard technical problem. It is **not yet a build contract**: many important journeys are only titles in `USER-FLOWS-INDEX.md:28-70`, and several “verified” ecosystem statements prove a listing, package, or deployed bytecode rather than a working end-to-end capability. The largest architecture error to avoid is showing a biometric prompt while the server retains an unrestricted signer and calling that a transaction-bound approval.

**Recommendation:** build a narrow business-operator journey that still feels like Abu's general Arc agent: voice or chat → contact clarification → bounded recurring USDC payout → decision record and notification, on both Arc networks. Add one real route-comparison decision. Keep the broader Arc inventory as a capability roadmap. Use Expo for the phone app, web for judge access, and an installable desktop web app as an explicitly named first desktop delivery. Gate unattended money movement on a funded, scoped-authority proof on **both** networks; if it does not pass, show attended scheduling honestly. This is my product and engineering judgment, grounded in Abu's required platforms and flows (`ABU-BRIEF-VERBATIM.md:15-47`) and the hackathon weights (`context/00-hackathon/judging-and-submission.md:7-23`).

## 5. Architecture critique and recommendation [OPINION]

### Authority: choose the boundary first

**A (Circle user wallet + developer-controlled allowance wallet)** is the fastest honest prototype, but its hard guarantee is only the funded allowance balance. The per-recipient and period rules are app logic, and a compromised backend signer can spend the whole allowance (`03-wallets-custody-limits/recommended-architectures.md:23-34,64-74`). It also introduces a custodial second balance and sweep/recovery burden. **C (Turnkey/Privy)** may put policy enforcement outside the app process, but the documented absence of rolling periods and unrun Arc path leave the “$10 every Tuesday” guarantee unresolved (`recommended-architectures.md:48-58,68-74`).

**B (passkey smart account + ERC-7710 delegation)** is the cleanest target for unattended action on both networks: the agent holds only the delegate key and the recipient, method, token, amount window and expiry are enforced in the redeem path (`recommended-architectures.md:36-46`; deployed-bytecode check above). The research correctly says its Arc runtime has **not** been proven with funds (`recommended-architectures.md:17-19,85-89`). The proposed A→hybrid-B path is reasonable **only if the allowance account itself is owned by the user's passkey and every outgoing transfer actually passes through the caveated redemption**. A Circle user-controlled vault cannot be assumed to install those caveats (`07-automations-contacts-safety/README.md:32-36`).

**My gate:** within two days, prove on testnet *and then mainnet with a user-authorized tiny amount*: owner creation/recovery, grant, authorized pay, period-boundary behavior, wrong recipient/method/token/native-value denial, over-budget denial, expiry, revoke, and a leaked-worker-key worst case. Verify the deployed source/audit scope before real value. State clearly that a weekly budget still permits a malicious delegate to spend at another time and possibly on either side of a period boundary; schedule discipline needs separate controls (`07-automations-contacts-safety/automations.md:50,58-60`). If that gate fails, ship attended recurring requests on testnet and describe A's allowance-balance cap accurately on mainnet; do not claim per-period or per-recipient limits are beyond the agent's reach. No root signer belongs in the worker. This directly addresses the earlier failure where the limited account was not the spender (`08-arc-agent-baseline-and-fit/what-was-learned.md:77-85`).

**Approval binding:** `expo-local-authentication` is a device-local prompt with a success/error result ([Expo API](https://docs.expo.dev/versions/latest/sdk/local-authentication/)). It does **not** sign `hash(draft)`. Under B, have the wallet/passkey sign a typed, domain-separated grant or transaction covering chain ID, account, recipient, asset, integer amount, nonce, expiry, schedule/limit and draft version. Under A/C, have the backend verify a separate device-held signing credential or the wallet's actual transaction authorization; an app-displayed Face ID success alone is insufficient to constrain a custodial signer. The “voice proposes, screen confirms” policy remains right (`05-voice-language-genui/voice-safety-confirmation.md:52-80`).

### One brain, voice, client

One shared intent/policy/execution service across chat, voice and Telegram is a sound direction (`00-SYNTHESIS.md:42-51`; `09-voice-decision/architecture-options.md:17-40`). **One model function is not enough:** all surfaces need the same durable `intent_id`, `draft_version`, policy decision, approval state and receipt. LiveKit RPC should be an ephemeral UI delivery channel; persist the canonical card/draft on the backend so reconnect, another device, or a closed sheet can resume safely. Reject delayed voice corrections against an older draft, and never let audio announce “sent” before a witnessed outcome (`09-voice-decision/architecture-options.md:82-91`; `07-automations-contacts-safety/automations.md:86-92`).

LiveKit plus a cascaded STT → shared `agentTurn` → TTS path is the best *provisional* voice choice because its Expo integration is documented and it keeps the money reasoner shared (`09-voice-decision/README.md:15-27`; [LiveKit Expo guide](https://docs.livekit.io/transport/sdk-platforms/expo/)). It is not a “guaranteed” quality path: phone latency, French money-intent accuracy, barge-in and UI round trips have not been measured (`09-voice-decision/README.md:43-50`). Run the phone spike before building the full catalog. Treat GPT-Live delegation as an experiment; the official model exists, but paraphrased spoken amounts and transcript-event ordering require separate acceptance (`09-voice-decision/architecture-options.md:118-145`). Keep a deterministic on-screen amount and recipient as the authority.

Expo is justified for iOS/Android and web; SDK 57 is listed as stable by Expo ([Expo SDK reference](https://docs.expo.dev/versions/latest/)). A PWA can satisfy a *desktop use case* quickly, but it is not proof of the “desktop application” Abu requested (`ABU-BRIEF-VERBATIM.md:15`; `06-mobile-desktop-platform/recommended-stack.md:12-15`). Label the first release “desktop web app,” then make native shell packaging a later acceptance item with passkey/login tested in that shell. The `recommended-stack.md:19-20` voice/wallet rows still contradict the later `09-voice-decision/README.md:15-27` and `03-wallets-custody-limits/recommended-architectures.md:76-85`; planning should use one consolidated decision record, not both as current guidance.

### Automation executor and reliability

Server-side scheduling is right because phone background execution is deferred (`06-mobile-desktop-platform/backend-jobs-and-automations.md:17-19`). Vercel Workflows may be a viable clock/retry engine (`backend-jobs-and-automations.md:20-50`), but its proposed one-long-running-workflow-per-automation loop is not itself a payment ledger. Use a database uniqueness constraint on `(automation_id, version, scheduled_for)`, a transactional claim/lease, a persisted immutable payment intent, and an outbox for notification. The worker checks current version, signed grant, contact address version, balance/reserved funds and quote immediately before submission. On a timeout after submission, reconcile by provider idempotency key **or chain nonce/tx hash** and never blindly replay (`07-automations-contacts-safety/automations.md:71-92`). A UUID alone cannot make a raw on-chain transfer idempotent; the research's provider-key semantics must not be applied to every execution path (`FEATURE-INVENTORY.md:90-97`). Test crash at every transition and competing occurrences before a live recurring payment.

## 6. Scope and hackathon fit [OPINION]

The organizer snapshot weights agentic decisions and traction at 30% each, Circle tools and innovation at 20% each; it asks for genuine business use and values mainnet transactions more than testnet (`context/00-hackathon/judging-and-submission.md:7-23`). The live event page still showed “October 10, 11:59 PM ET” when fetched on 2026-09-29 (`curl -LsS https://tameion.thecanteenapp.com/ | rg 'October 10, 11:59 PM ET'`). A consumer “do everything” wallet is allowed, but the business-operator framing aligns more directly with those criteria (`08-arc-agent-baseline-and-fit/hackathon-fit.md:17-48`).

**Ship one decision story:** a freelancer/small studio receives USDC, asks by voice in French or English to pay a known contractor every Tuesday, the agent resolves or pauses for a new contact, checks cash reserve and a bounded grant, pays or escalates, then shows a receipt and “why” record. Prove unattended authority first for a same-chain Arc USDC transfer; show crosschain route comparison and require a fresh attended signature for bridging until its call policy is separately proven. This uses Abu's voice, automation, contacts, bridge, language and both-network requirements (`ABU-BRIEF-VERBATIM.md:15,39,47`) and demonstrates an actual decision rather than a cron job (`context/00-hackathon/judging-and-submission.md:9-14,27-36`).

**Release boundary:** (1) deployed web judge path plus a real Android/iOS development build; (2) the same core journey on mainnet and testnet, with network-specific availability visible; (3) one live, small-value business payment or honest testnet proof with tx hashes; (4) voice on an actual phone in English/French; (5) grant negative tests and recovery; (6) public repo and <3-minute video (`context/00-hackathon/judging-and-submission.md:38-48`). ## 7. Where I agree with Claude

- **Authority, not cron, is the central risk.** Circle user-controlled wallets need user-present signing; a backend signer with app-only rules is not a hard per-recipient limit (`03-wallets-custody-limits/README.md:20-25`; `07-automations-contacts-safety/automations.md:18-25`).
- **Mainnet/testnet need a capability registry.** LI.FI lists both while Relay and x402 Discovery do not offer the same testnet surface (live API checks above); one network switch must never silently reinterpret an intent (`00-SYNTHESIS.md:42-50`).
- **Typed proposals and deterministic policy are right.** The model must not invent an address or turn untrusted service content into authority (`FEATURE-INVENTORY.md:154-176`; `05-voice-language-genui/voice-safety-confirmation.md:52-69`).
- **A common agent core and native-rendered fixed card catalog are sound.** They avoid duplicated voice/chat policy and arbitrary generated executable UI (`00-SYNTHESIS.md:42-47`; `FEATURE-INVENTORY.md:136-152`).
- **The previous projects' failure modes are well identified.** Arc Copilot's limited account did not actually spend; KeeperHub's voice and chat reasoners diverge, and its UI patterns are still useful (`08-arc-agent-baseline-and-fit/what-was-learned.md:77-103`; `09-voice-decision/README.md:40-41`).
- **Deploy early and seek real usage.** The prior Arc project was not deployed, while the current rubric expressly rewards working business money flow (`08-arc-agent-baseline-and-fit/what-was-learned.md:26-37`; `context/00-hackathon/judging-and-submission.md:18-23`).
