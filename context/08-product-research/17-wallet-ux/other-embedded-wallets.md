## 1. Bottom line

- **No provider in this survey shows evidence of being tested on Expo SDK 57 / React Native 0.86.** The newest example app found is on Expo 54 / RN 0.81 (Dynamic, Para) [V]. Crossmint has an open, unmerged pull request moving its playground to "Expo SDK 57 (React Native 0.86.3)" [V]. So every verdict below carries a build risk that only a one-day spike removes [I].
- **Best fit: Dynamic.** Arc is a first-class ("Tier 1") chain on both networks, the headless JavaScript SDK is one package for web and React Native with TurboModules, the embedded wallet is an EOA that signs arbitrary EIP-7702 authorizations and EIP-712 data with no built-in modal, and a passkey (Face ID) prompt can be attached to signing as an option [V].
- **Second: Para.** Custom EVM chains by chain ID and RPC, an Arc walkthrough, `signAuthorization` on its viem account, native passkeys on React Native, transaction popups that can be switched off, and a session that can be exported to our server [V]. Its native signer module uses the old bridge style, which is the main risk on RN 0.86 [V fact, I risk].
- **Possible but weaker: thirdweb, Openfort, Magic, Web3Auth (MetaMask Embedded Wallets), Coinbase CDP.** Each can produce the three signatures on a custom chain, each has a specific weakness (old native dependencies, no native passkeys on React Native, browser-redirect login, or Arc only through raw signing).
- **Different design, not the spike-15 path: Crossmint** (smart-contract wallet, not an EOA).
- **Ruled out: Reown AppKit** (hosted iframe wallet, session lost when the app closes) and **Porto** (deprecated, repository archived).
- **Agent authority is provider-independent in our design** [I from spike 15]: the limit lives in an on-chain delegation signed once by the user's EOA, and our own server key redeems it. Provider-side "delegated access" or "server signers" are therefore optional extras, and several are paid (Dynamic: Enterprise in production).

## 2. Providers

### 2.1 Dynamic

1. **User experience.** Sign-in by email OTP, SMS, social or passkey; a passkey can only be used for sign-in after the user has signed in another way and registered it (`dynamic/javascript_authentication-methods_passkey.md`) [V]. The JavaScript SDK is headless: "no built-in modal, wallet picker, or login form" (`dynamic/javascript_overview.md`) [V]; the old confirmation modal "is gone" and the app builds its own review step (`dynamic/javascript_migrating-from-react_transactions-and-balance.md`) [V]. So signing is silent unless we add a step [I]. Optional "Action-Based MFA" can require a passkey or TOTP check on "WaaS Sign - When any signature is performed i.e. a message, a transaction, typed data, authorization" (`dynamic/javascript_authentication-methods_mfa_action-based.md`) [V]. That gives a Face ID prompt per signature only if we want one.
2. **React Native / Expo.** `@dynamic-labs-sdk/client` 1.36.0 (published 2026-09-29), with `@dynamic-labs-sdk/evm` and `@dynamic-labs-sdk/react-hooks` [V]. It declares `codegenConfig` (TurboModules) and ships Swift/Kotlin key managers; native peers are `react-native-keychain ^10.0.0`, `@react-native-async-storage/async-storage ^2.2.0`, and optionally `react-native-passkey >=3.3.2` and `react-native-inappbrowser-reborn ^3.7.0` (`dynamic-client-tarball.txt`) [V]. Expo development build required; "Expo Go is not supported" (`dynamic/javascript_react-native_expo.md`) [V]. Passkeys on React Native through `react-native-passkey`, with our own domain hosting the `apple-app-site-association` and `assetlinks.json` files (`dynamic/javascript_react-native_passkeys.md`) [V]. The same package runs on the web ("runs in React Native the same way it runs on the web", `dynamic/javascript_react-native_setup.md`) and its exports carry a `react-native` condition [V]. Example app `dynamic-labs-oss/expo-via-js-example-app`: Expo 54.0.31, RN 0.81.4, `newArchEnabled: true`, SDK ~1.18.0 [V]. Expo 57 / RN 0.86: no evidence [U]. Do not confuse with the older WebView-based `@dynamic-labs/legacy-client` [V].
3. **Arc.** Tier 1 chain table lists "Arc | Yes | Yes | Yes | Yes" (send and sign, gasless, on-chain events, delegated access) for JavaScript, React and React Native (`dynamic/embedded-wallets_chains_overview.md`) [V]. The gas sponsorship table lists "Arc | Mainnet | `5042`" and "Arc Testnet | Testnet | `5042002`" (`dynamic/embedded-wallets_gas-sponsorship.md`) [V]. Our own RPC: the client option `transformers.networksData` can "override RPC URLs, restrict which networks are available, control the default network, or add a custom network" and "applies to all operations (balance fetching, transactions, RPC client creation)" (`dynamic/javascript_reference_networks_network-transformers.md`) [V]. Whether a free environment shows Arc in the dashboard network list without contacting Dynamic: [U] (needs an account).
4. **Account type.** EOA whose key is split by TSS-MPC (user share on the device, server share in a TEE) (`dynamic/embedded-wallets_mpc_overview.md`) [V]. EIP-7702: `sign7702Authorization` signs for Dynamic's own delegation contract [V]; the embedded EVM provider also has a generic viem-style `signAuthorization({ parameters })` taking `SignAuthorizationParametersWithoutPrivateKey`, i.e. any contract address (`tarball-and-gh-evidence-2026-09-30.txt`) [V typing, not executed]. EIP-712 through `createWalletClientForWalletAccount` then `walletClient.signTypedData` (`dynamic/javascript_reference_evm_sign-typed-data.md`) [V].
5. **Agent authority.** Delegated Access hands our server an encrypted key share and a per-wallet API key after the user approves; "For production use, delegated access requires an Enterprise plan" (`dynamic/embedded-wallets_mpc_delegated-access_overview.md`) [V]. Policies (allow/deny lists, `valueLimit.maxPerCall`) are enforced in a TEE; the wallet and signer layers are "early access" (`dynamic/embedded-wallets_mpc_policies_overview.md`) [V]. No cumulative or daily limit field appears in the rule table [V absence]. Server wallets (Node, Python, Rust, Java) and "agent wallets" (a server agent signing as a Dynamic user) also exist (`dynamic/agents_overview.md`) [V].
6. **Price and gates.** "Free to start up to 1,000 MAUs"; an Enterprise column with "Talk to sales" (`pricing/dynamic.txt`) [V]. Testnet gas sponsorship "on every plan"; "Sponsoring mainnet transactions requires an Enterprise plan" (`dynamic/javascript_reference_evm_evm-gas-sponsorship.md`) [V]. No KYC or business verification on the pricing page [V absence].
7. **Verdict: yes, the strongest candidate here.** Everything we need is in the self-serve tier and Arc is named on both networks; the open risk is the untested Expo 57 build.

### 2.2 Para (getpara)

1. **User experience.** Email or phone OTP, OAuth, then a passkey, password or PIN as the wallet's auth method (`para-llms-full.txt:2117`) [V]. Signing uses a session: "Session length is configured per API key", up to 30 days, and signing can extend it (`:6442`) [V]. Transaction popups are a per-key setting: `--transaction-popups` / `--no-transaction-popups` (`:2118-2119`) [V]. With popups off, or with a matching permissions policy, signing returns directly; otherwise the SDK hands back a `transactionReviewUrl` to open (`:17330`, `:33575`) [V].
2. **React Native / Expo.** `@getpara/react-native-wallet` 3.20.0 (published 2026-09-29) [V]. "bare workflow or Expo development build (managed workflow is not supported)" (`:25170`) [V]. Native passkeys through `react-native-passkey`; iOS needs Associated Domains and our Team ID and bundle ID registered in Para's developer portal (`:1200`, `:7266-7280`, the second from the Flutter guide) [V]. The native signer is an old-style bridge module (`ReactContextBaseJavaModule`, no `codegenConfig`) and it requires `react-native-modpow` 1.1.0, last published 2023-01-18 (`example-app-versions-2026-09-30.txt`, `tarball-and-gh-evidence-2026-09-30.txt`) [V]. Whether both still load on RN 0.86: [U]. Example `getpara/examples-hub/mobile/with-expo-one-click-login`: Expo ^54, RN 0.81.5 [V]. The web app uses a different package (`@getpara/react-sdk`), so Expo web needs platform-split files [I].
3. **Arc.** Official walkthrough "Integrate Arc Chain with Para" configures Arc Testnet 5042002 as a custom chain (`para/walkthrough-arc.md`) [V]; mainnet is not shown. "To add support for any additional chains within these networks, include its chain ID ... and RPC endpoint" (`:10319`) [V], so mainnet 5042 is a config entry [I].
4. **Account type.** EOA, 2-of-2 MPC (user share on device, Para share in HSMs) (`:3057`, `:3099`) [V]. EIP-7702: the viem account exposes `signAuthorization` (`signAuthorization: async (auth) => viemParaAccount.signAuthorization(auth)`, `:778`) [V]. EIP-712 and transactions through `@getpara/viem-v2-integration` [V].
5. **Agent authority.** `para.exportSession()` on the client, `serverPara.importSession(sessionString)` on the server: "Server can now sign on behalf of the user" while the session lasts (`:1050-1058`) [V]. Permissions policies include `WINDOWED_SPEND_LIMIT`, which "Tracks cumulative automatic signing attempts for a fixed time window" for native and ERC-20 `transfer` (`:3403-3409`) [V]. Which plan includes the server SDK and policies: the earlier file records Starter ($200/month) [V 2026-09-29, not rechecked].
6. **Price and gates.** Free "Up to 1,200 MAUs", "REST API usage up to 30 req/min", 1 project; Starter $200/month; Enterprise "Book A Call" (`pricing/para.txt`) [V]. "Native Passkeys" is listed under Starter; whether the free plan includes them is not stated [U].
7. **Verdict: maybe, competitive.** The feature set matches closely (silent signing in a session, native passkeys, 7702, server session); the old-style native module on RN 0.86 and the separate web package are the risks.

### 2.3 thirdweb (in-app wallets)

1. **User experience.** Email, phone, social, passkey, guest, custom JWT (`thirdweb/wallets_users.txt`) [V]. `inAppWallet().connect({ strategy })` returns an account object; its `signTypedData`, `signTransaction`, `sendTransaction` and `signAuthorization` call thirdweb's enclave directly (`thirdweb-tarball.txt`, `tarball-and-gh-evidence-2026-09-30.txt`) [V code]. No mandatory modal in that path [I].
2. **React Native / Expo.** One package for web and native: `thirdweb` 5.121.6 plus `@thirdweb-dev/react-native-adapter` 1.5.5 (last published 2026-03-26) [V]. Development build required; "Expo Go is not currently supported" (`thirdweb/react-native_v5_getting-started.txt`) [V]. Passkeys through `react-native-passkey` [V code]. Required native peers include `react-native-aes-gcm-crypto` 0.2.2, last published 2022-07-20, with no `codegenConfig` [V]. Starter `thirdweb-dev/expo-starter`: Expo 53.0.13, RN 0.79.2, last push 2025-08-13 [V]. Expo 57: [U].
3. **Arc.** Chain API returns 5042 "Arc" and 5042002 "Arc Testnet" (`thirdweb-chains-2026-09-30.txt`) [V]. The SDK exports `arcTestnet` only; mainnet needs `defineChain(5042)` [V earlier file].
4. **Account type.** EOA held in thirdweb's enclave; `account.signAuthorization({ address, chainId, nonce })` accepts any delegate address [V code]. thirdweb's own "EIP7702" execution mode fetches its delegate contract from its bundler (`tw_getDelegationContract`); whether that bundler serves Arc is [U] and not needed for our design.
5. **Agent authority.** Session keys on the 7702 account with call and transfer policies (`LimitType.Lifetime`, `LimitType.Allowance` with a period), used by a server wallet (`thirdweb/wallets_session-keys.txt`) [V docs]; depends on the point above for Arc [U].
6. **Price and gates.** The pricing page fetched today shows Growth $99/month, Scale $499/month, Pro from $1,499/month, and "First 1000 wallets free" then $0.015 per MAU; the words "free plan", "starter" and "trial" do not appear (`pricing/thirdweb.txt`, `pricing/thirdweb-pricing-2026-09-30.html`) [V]. Whether a project can run without a paid plan: [U].
7. **Verdict: maybe.** The signing surface fits and Arc is listed, but the React Native dependency set is old and the entry price is unclear.

### 2.4 Openfort

1. **User experience.** Email/password, OTP, social, then a wallet "recovery method": automatic, password or passkey (`openfort-llms-full.txt:68-70`) [V]. Passkey recovery on React Native "requires **iOS 18+** or **Android 14+ (API 34)**" because it uses the WebAuthn PRF extension (`:10547`) [V]. Per-signature prompt behaviour after the wallet is recovered is not described on the pages read [U].
2. **React Native / Expo.** `@openfort/react-native` 2.2.0 (published 2026-09-26); peers are Expo modules plus `react-native-webview`; it bundles `react-native-passkeys` 0.4.1 [V]. The key shares run in a WebView (PR "recover the embedded wallet WebView when it stops responding", 2026-07) [V]. The SDK's own dev dependencies are RN 0.77.1 and Expo-52-era modules [V]. Expo 57: [U]. Web uses `@openfort/react` (separate package) [V].
3. **Arc.** Not in Openfort's supported-chain list (earlier file, 2026-09-29) [V]. But "EOA wallets are Ethereum-chain-agnostic in Openfort ... even ones that are not part of the built-in chain list" with `accountType: AccountTypeEnum.EOA` and a viem `defineChain` (`:3736-3740`, `:7113`) [V]. So Arc works as plain EOA signing on both networks [I]; no Openfort bundler, paymaster or default delegate there [I].
4. **Account type.** EOA, smart account, or "delegated account" (7702). On an unsupported chain "you can still delegate to any 7702 implementation deployed on that chain by signing the authorization yourself with viem", using `client.embeddedWallet.signMessage(hash, { hashMessage: false })` on `hashAuthorization(...)` (`:12610`, `:12700+`) [V]. A `signTypedData` helper was added in 2026-07 (PR #102) [V].
5. **Agent authority.** Backend wallets and a policy engine exist (`pricing/openfort.txt`, docs) [V]; tied to supported chains for sending [I].
6. **Price and gates.** Free: "2,000 ops included · then $0.01/op"; "Payment method required to continue past 2,000 operations" (`pricing/openfort.txt`) [V]. A payment is about two operations [V].
7. **Verdict: maybe.** A clean Expo-modules SDK with documented manual 7702 signing; passkeys need recent OS versions, and Arc is only reachable as raw EOA signing.

### 2.5 Magic

1. **User experience.** Email OTP, SMS, social; custom UI with `showUI: false` (`magic-llms-full.txt:1092-1112`) [V]. "EIP-7702 operates headlessly with no UI confirmation prompt" (EIP-7702 guide) [V]. Passkey login is an extension of the **web** SDK ("available via the `Passkey` extension of the Web client-side SDK") [V]; native passkeys on React Native: none found [U].
2. **React Native / Expo.** `@magic-sdk/react-native-expo` 34.12.0 (published 2026-09-01); peers are `react-native-webview`, `react-native-safe-area-context`, netinfo [V]. The wallet runs inside a WebView "Relayer" component that must be mounted in the app (`:13019`) [V]. It depends on `@react-native-async-storage/async-storage` ^1.15.5 while Expo 57 bundles 2.2.0 (`expo57-compat.txt`) [V]. Past issue #897, "native bridge calls hang indefinitely on Android with Expo SDK 53 + React Native 0.79 + New Architec…", closed 2025-06-14 [V]. Expo 57: [U]. Web uses `magic-sdk` (separate package) [V].
3. **Arc.** No Arc artefact; custom node by `rpcUrl` + `chainId`, and the RPC URL must be added to the project's content security policy in the dashboard (`:4159-4182`) [V]. Same mechanism for both networks [I].
4. **Account type.** EOA, key in Magic's TEE key system (`:8664`) [V]. `magic.wallet.sign7702Authorization({ contractAddress, chainId, nonce? })`, available from `@magic-sdk/react-native-expo@34.2.0` (`:11734-11772`) [V].
5. **Agent authority.** "Server Wallets (Core and Express)" appear in the pricing comparison [V]; no delegated signing of a user's wallet found [U].
6. **Price and gates.** Developer plan $0: "1,000 Monthly Active Wallets + 50,000 signatures"; Startup $99/month (`pricing/magic.txt`) [V]. "Advanced MFA: SMS, WebAuthn, Threat Based, Step-Up" is a row in the plan comparison; which plan includes it cannot be read from the text capture [U].
7. **Verdict: maybe.** The 7702 method is the most direct of all, but the wallet lives in a WebView and there is no native passkey, so the "Face ID" feel would be ours to add.

### 2.6 Web3Auth / MetaMask Embedded Wallets

1. **User experience.** Login "opens an in-app browser so the user can authenticate" and returns by deep link; a custom JWT (`idToken`) skips the browser (`metamask-llms-embedded-wallets-sdk-full.txt:16950`, `:17447`) [V]. Custom authentication in production needs the Growth plan (`:586`) [V]. Passkeys exist only as an MFA factor (`passkeysFactor`) [V]. After login the app holds an EIP-1193 provider, and on mobile SDKs "the private key is available in the user scope" (`metamask/arc.md`) [V], so signing is silent and local [I].
2. **React Native / Expo.** `@web3auth/react-native-sdk` 10.0.0 (published 2026-08-17); "Expo SDK 48 or later"; no Expo Go (`:16536-16650`) [V]. Peer `react-native-quick-crypto` [V]. Example repo on Expo 51 / RN 0.74.1 [V]. Expo 57: [U]. Web uses `@web3auth/modal` 11.4.2 [V].
3. **Arc.** A docs page "Integrate Embedded Wallets with the Arc Blockchain" exists with React Native instructions; its chain details list only testnet 5042002 (`metamask/arc.md`, `metamask/arc-react-native.md`) [V]. Mainnet by custom chain config [R, earlier file].
4. **Account type.** EOA; with the raw key, viem's local account can sign a 7702 authorization, EIP-712 and transactions [I]. No provider method named for 7702 [U].
5. **Agent authority.** None found for acting on a user's wallet [U].
6. **Price and gates.** Free 1,000 monthly active wallets (earlier file) [V 2026-09-29]. Several features are "free on `sapphire_devnet`" and paid in production [V].
7. **Verdict: maybe, weak fit.** Technically the simplest signer, but the key sits in JavaScript memory and the login is a browser round trip, which is not the experience the product owner asked for [I].

### 2.7 Coinbase CDP embedded wallets

1. **User experience.** Email OTP, SMS, social [V]. "Passkey MFA is supported in **web environments only**" (`cdp/mfa-passkeys.md`) [V]. Signing calls are plain SDK functions [V].
2. **React Native / Expo.** `@coinbase/cdp-core`, `@coinbase/cdp-hooks`, `@coinbase/cdp-react-native` 0.0.126 (published 2026-09-18); "Works seamlessly with managed and bare Expo workflows" (`cdp/react-native.md`) [V]. Optional peers `expo-secure-store ^15.0.0` and `expo-web-browser ^15.0.0`, while Expo 57 bundles `~57.0.4` and `~57.0.3` (`expo57-compat.txt`) [V]; demo app on Expo 53 / RN 0.79.6 [V]. Same core package has `web` and `native` builds [V].
3. **Arc.** Not in any network enum (`sendEvmTransaction`: base, ethereum, avalanche, polygon, optimism, arbitrum, world and testnets) [V]. "`sendTransaction` is supported on Base, Ethereum, Avalanche, Polygon, Optimism, and Arbitrum. For other chains, use the sign transaction feature" (`cdp/send-transactions-head.md`) [V]. So Arc means sign-only on both networks plus our own broadcast [I].
4. **Account type.** EOA (or Coinbase smart account) [V]. `createEvmEip7702Delegation` is limited to seven named networks, none Arc [V]. `signEvmHash` exists, so an authorization digest could be signed by hand [I, not tested]; `toViemAccount` has no `signAuthorization` [V code].
5. **Agent authority.** Delegated signing: the user grants a time-bound delegation, then the backend calls `signEvmTransaction`, `signEvmTypedData` and others with no user present (`cdp/delegated-signing.md`) [V]. No plan gate stated on the pricing page [V absence].
6. **Price and gates.** $0.005 per wallet operation; "The first **5,000 wallet operations per month** are free" (`cdp/pricing.md`) [V]. "business verification is not required" (earlier file) [V 2026-09-29].
7. **Verdict: maybe, weak.** Free and with real delegated signing, but Arc is reachable only through raw signing and there are no passkeys on mobile.

### 2.8 Crossmint

1. **User experience.** Email OTP or Google sign-in; the wallet then uses a "device" signer: "Hardware-backed, no OTP. **Browser and React Native only**"; the passkey signer is "Browser (EVM only)" (`crossmint-llms-full.txt:79078-79082`) [V]. Email or phone OTP is the recovery method [V].
2. **React Native / Expo.** `@crossmint/client-sdk-react-native-ui` 1.7.1 (published 2026-09-25), an Expo module with Swift and Kotlin device-signer code [V]. It hard-depends on `expo-secure-store ~15.0.7`, `expo-web-browser ~15.0.8`, `react-native-webview 13.15.0` (`expo57-compat.txt`) [V]; Expo 57 bundles 57.x versions of the first two, so duplicate native modules are likely [I]. Open PR #2112 "chore(playground): Expo SDK 57 (React Native 0.86.3)", created 2026-09-28, not merged [V].
3. **Arc.** Listed for wallets on mainnet (`arc`) and testnet (`arc-testnet`) (earlier file) [V 2026-09-29].
4. **Account type.** Smart-contract wallet with signers; not an EOA [V]. EIP-7702 authorization signing: not applicable [I].
5. **Agent authority.** A server signer is added with scoped permissions ("spend cap, allowed counterparties, and a time window", "enforced onchain"), approved once by the user with an email code, then "no user prompt per transaction" (`:1027`, `:3914`, `:3991`) [V docs].
6. **Price and gates.** "Free 1,000 Monthly Active Wallets", "Up to 2,000 transactions"; "Delegated signers" and "Policy engine" appear in the feature comparison without a clear tier in the text capture (`pricing/crossmint.txt`) [V, tier U].
7. **Verdict: maybe, but it is a different architecture.** It has its own prompt-free device signer and on-chain agent permissions on Arc, yet it replaces the spike-15 design (contract wallet, their API) and would need its own proof on Arc.

### 2.9 Reown AppKit (email and social wallet)

- The embedded wallet "signs inside an iframe hosted at `secure.walletconnect.org`" and is limited to chains on Reown's Blockchain API (`reown/chain-support-layers.md`) [V]. That API lists `eip155:5042` and `eip155:5042002` (`reown/blockchain-api-supported-chains-2026-09-30.json`) [V].
- React Native: `@reown/appkit-react-native` 2.0.6 (published 2026-07-14). The docs state: "Due to Safari's strict third-party cookie policies, the SDK is not preserving sessions after the app is closed" (`reown/react-native-email.md`) [V]. OTP is pasted "in the modal" [V].
- "Headless mode" is a Pro feature ($89/month); free tier 500 MAU (`pricing/reown.txt`) [V]. No server signer for a user's wallet found [U].
- **Verdict: no.** Hosted modal wallet that forgets the session on mobile; keep AppKit only for connecting external wallets.

## 3. What the "Tempo wallet" experience is

- Tempo Wallet is "Tempo's web-based passkey wallet" at wallet.tempo.xyz (`tempo-llms-full.txt:273`) [V]. The demo flow is "sign in with a passkey and get a Tempo address" (`:2884`) [V].
- The chain itself accepts passkey signatures: Tempo Transactions are a new transaction type (`0x76`) "with WebAuthn signatures, parallelizable nonces, gas sponsorship, and batching" (`:93`, `:12532`) [V]. No smart-contract account is needed for that [I].
- **Access keys**: the main key signs one authorization for a secondary key (for example a device-bound WebCrypto key) with an expiry, per-token spending limits with a period, and call scopes; after that the access key signs alone (`:10636-10643`, example with `Expiry.hours(1)`, a 1000-token monthly limit and a `transfer` scope at `:10716-10735`) [V]. The Accounts SDK describes this as submitting "transactions without prompts" (`tempo-accounts-readme.md`) [V].
- **Fees**: paid in stablecoins, and a separate fee payer can sponsor a transaction (`:19578`) [V].
- The SDK is the npm package `accounts` 0.19.0 (published 2026-09-29); its peers are Expo 55 modules (`expo-secure-store ^55.0.12`) and `viem >=2.56.9`; it targets Tempo [V], so it is not usable on Arc [I].
- **What carries over to Arc** [I, based on spike 15]: (a) access keys map to our EIP-7702 delegation with caveats (token, method, amount per period, expiry), already proven on Arc testnet; (b) "no prompt inside the limit" is the same result; (c) sponsored setup maps to our relayer sending the type-4 transaction; (d) stablecoin fees are native on Arc (gas is USDC).
- **What does not carry over** [I]: a passkey as the account's own signature type. On Arc a passkey can only unlock or approve an ordinary key (Dynamic, Para, Openfort, Privy, Turnkey) or control a smart-contract account (see `passkey-accounts-on-arc.md`).

## 5. Gaps

1. **Expo SDK 57 / RN 0.86.3 is untested for every provider.** No changelog, issue or example naming SDK 57 was found except Crossmint's open PR. A build spike (install, prebuild, launch on iOS and Android, sign one message) is the only way to close this, starting with Dynamic, then Para.
2. **Dynamic**: whether a free (non-Enterprise) environment lists Arc mainnet and testnet in the dashboard (the client-side network transformer is the fallback); whether the generic `signAuthorization` works for the MetaMask `EIP7702StatelessDeleGator` address in practice; whether the MPC signing runs natively or in a hidden WebView on React Native (the package ships a `NativeDynamicWebView` TurboModule); passkey sign-in needs a first sign-in by another method, so onboarding is email or social first, passkey second.
3. **Para**: whether the old-style native signer module and `react-native-modpow` load on RN 0.86; which plan includes native passkeys, the server SDK and permissions policies; Arc mainnet is an inference from the custom-chain rule.
4. **thirdweb**: whether a free plan still exists; whether its bundler and delegate contract serve Arc; whether `react-native-aes-gcm-crypto` (2022) builds on RN 0.86.
5. **Openfort**: what the user sees per signature after recovery; whether automatic recovery needs our backend; passkey recovery excludes iOS 17 and Android 13 devices.
6. **Magic**: no native passkey on React Native was found; the async-storage 1.x dependency against Expo 57's 2.2.0 is unresolved.
7. **Coinbase CDP**: whether `signEvmTransaction` accepts an arbitrary chain ID such as 5042, and whether `signEvmHash` is allowed for end-user accounts under default policies.
8. **Crossmint**: smart-wallet factory and bundler on Arc were not checked on-chain (open since 2026-09-29); tier for delegated signers unclear.
9. **No provider's per-signature behaviour was observed on a device.** "Silent" is read from docs and code, not seen.
10. Firecrawl credits used in this run: 0 (curl, `npm pack`, `gh api` and the earlier run's files only).
