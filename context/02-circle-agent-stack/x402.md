## Protocol in one screen

x402 = HTTP-native payment negotiation on status `402 Payment Required` (spec: x402.org, docs.x402.org, reference impl github.com/coinbase/x402). It is not a payment system; schemes/facilitators decide how money moves. "No accounts, no API keys: the payment is the authentication."

| Header (v2) | Direction | Content (base64 JSON) |
|---|---|---|
| `PAYMENT-REQUIRED` | server → client, on 402 | `{x402Version:2, resource:{url,description,mimeType}, accepts:[PaymentRequirements…]}` |
| `PAYMENT-SIGNATURE` | client → server, retry | `{x402Version:2, resource, accepted:<chosen requirement>, payload:{signature, authorization}, extensions?}` |
| `PAYMENT-RESPONSE` | server → client, with 200 | settlement confirmation (tx hash) |

v1 (legacy, still seen in marketplace): headers `X-PAYMENT` / `X-PAYMENT-RESPONSE`, `network:"base"` names, `maxAmountRequired` instead of `amount`.

PaymentRequirements (v2):
```json
{"scheme":"exact","network":"eip155:5042002","amount":"1000000","asset":"0x3600000000000000000000000000000000000000",
 "payTo":"0xSeller","maxTimeoutSeconds":12,"extra":{"name":"USDC","version":"2"}}
```
- `extra.name == "GatewayWalletBatched"` ⇒ Gateway nanopayment option (sign against GatewayWallet domain); otherwise vanilla (sign against the USDC token's EIP-712 domain).
- Amounts are USDC base units (6 decimals): $1 = `1000000`, $0.01 = `10000`.
- Roles: buyer (agent), seller (HTTP API), facilitator (verifies/settles; optional).

## Circle's two facilitators

| | Facilitator Service | Gateway Nanopayments |
|---|---|---|
| Settlement | onchain per payment via Circle relayer (`transferWithAuthorization`) | batched net settlement (TEE-signed) |
| Min payment | standard USDC transfer | $0.000001 |
| Chains | Arc, Base, Polygon PoS (+ testnets) | Gateway-supported EVM chains (Arc, Base, Eth, Arb, OP, Polygon, Avax, Unichain, Sonic, Sei, HyperEVM, World Chain…) |
| Gas | Circle pays settlement gas | zero (offchain signatures) |
| Buyer setup | EOA (or deployed ERC-1271 SCA) holding USDC | one-time deposit into Gateway Wallet; EOA signatures only |
| Seller auth | Circle API key, or keyless trial w/ `Facilitator-Seller-Proof` | none needed (`BatchFacilitatorClient`) |
| Screening | both parties screened before settlement | (Marketplace screens sellers) |
| API base | `https://api.circle.com/v1/facilitator/x402/` | `https://gateway-api[-testnet].circle.com/v1/x402/` |

Both use scheme `exact` with EIP-3009 `TransferWithAuthorization`; a client that pays one can pay the other without code change.

## Facilitator Service (launched 2026-09-16)

Endpoints (`https://api.circle.com`):

| Method | Path | Notes |
|---|---|---|
| GET | `/v1/facilitator/x402/supported` | public; lists kinds (live: Arc 5042 & 5042002, Base 8453 & 84532, Polygon 137 & 80002) |
| POST | `/v1/facilitator/x402/verify` | validates payload; no charge, no trial usage, nothing onchain |
| POST | `/v1/facilitator/x402/settle` | validates, screens, records, submits; **always HTTP 200** — terminal success or `success:false, errorReason:"settlement_pending"` + `paymentId` |
| GET | `/v1/facilitator/x402/status/{paymentId}` | `pending` \| `completed` \| `failed` (`reason=reorged` possible on Base) |

Auth: Circle API key in production. **Keyless trial**: per-`payTo`, per-chain allowance (testnet and mainnet counted separately); seller account auto-created on first `/settle`; exhausted → `HTTP 403 registration_required`; settling once with an API key binds the seller account to your Circle account (history carries over).

Keyless requests carry `Facilitator-Seller-Proof: <base64url(JSON envelope)>`, an EIP-712 signature by the key controlling `payTo`:
```ts
domain = { name: "Circle Facilitator Seller Request", version: "1", chainId: 5042002 }   // EIP-155 id of the payment network
types = { SellerRequest: [
  {name:"purpose",type:"string"}, {name:"method",type:"string"}, {name:"bodyHash",type:"bytes32"},
  {name:"network",type:"string"}, {name:"payTo",type:"address"}, {name:"nonce",type:"bytes32"},
  {name:"issuedAt",type:"uint64"}, {name:"expiresAt",type:"uint64"} ] }
message = { purpose:"settle"|"verify"|"status", method:"POST", bodyHash: keccak256(toBytes(rawBody)) /* GET: empty bytes */,
            network:"eip155:5042002", payTo, nonce: toHex(random32), issuedAt, expiresAt: issuedAt+300 }
envelope = { version:1, signature, network, payTo, nonce, issuedAt, expiresAt }  // → Buffer.from(JSON).toString("base64url")
```
Rules: purpose must match route; network/payTo must equal `paymentRequirements` (else 401); `issuedAt` ≤ 30 s in future; `expiresAt` ≤ 5 min after `issuedAt`; nonce unique per (network, payTo) across purposes (exact retries may reuse). EOA recovered to `payTo`, or ERC-1271 for deployed SCA.

`/settle` body:
```json
{"x402Version":2,
 "paymentPayload":{"x402Version":2,
   "resource":{"url":"https://api.example.com/premium","description":"Premium report","mimeType":"application/json"},
   "accepted":{"scheme":"exact","network":"eip155:5042002","amount":"1000000","asset":"0x3600000000000000000000000000000000000000",
               "payTo":"0xSeller","maxTimeoutSeconds":12,"extra":{"name":"USDC","version":"2","assetTransferMethod":"eip3009"}},
   "payload":{"signature":"0x…","authorization":{"from":"0xBuyer","to":"0xSeller","value":"1000000","validAfter":"0","validBefore":"1781308800","nonce":"0x…"}},
   "extensions":{"payment-identifier":{"info":{"required":true,"id":"pay_5f0d3c1a9b7e4d2c"}}}},
 "paymentRequirements":{"scheme":"exact","network":"eip155:5042002","amount":"1000000","asset":"0x3600000000000000000000000000000000000000",
   "payTo":"0xSeller","maxTimeoutSeconds":12,"extra":{"name":"USDC","version":"2"}}}
```
```bash
curl -X POST https://api.circle.com/v1/facilitator/x402/settle -H "Facilitator-Seller-Proof: $PROOF" -H "Content-Type: application/json" -d @body.json
# success: {"success":true,"payer":"0x…","transaction":"0x…","network":"eip155:5042002","amount":"1000000"}
# pending: {"success":false,"errorReason":"settlement_pending","transaction":"", "extensions":{"settlement-status":{"status":"pending","paymentId":"…","statusUrl":"https://api.circle.com/v1/facilitator/x402/status/…"}}}
```
- **Idempotency**: `payment-identifier.id` 16–128 chars `[A-Za-z0-9_-]`; retries converge. Without it, a retry must reuse the exact same signed authorization or it's a new charge. Never re-sign a pending payment.
- **Do not fulfill on pending**; poll `/status` (your own cadence).
- Buyer EIP-3009 domain for Arc USDC: `{name:"USDC", version:"2", chainId:5042002 (testnet) | 5042 (mainnet), verifyingContract:"0x3600000000000000000000000000000000000000"}`. Base: name `"USD Coin"`.
- Finality: Arc instant; Base = L2 inclusion + receipt + Transfer event (reorg → `failed`, never auto-resubmitted); Polygon standard finality.
- Disclaimer: Circle Technology Services; does not verify transaction purpose or "confirm agent authority scope".

## Buyer side (vanilla, code)

CLI: `circle services pay <url> -X GET --address 0xAgent --chain ARC --max-amount 0.05`.

TypeScript with the Coinbase x402 packages (`@x402/fetch`, `@x402/evm`, `@x402/core` 2.27.0):
```ts
import { wrapFetchWithPaymentFromConfig, decodePaymentResponseHeader } from "@x402/fetch";
import { ExactEvmScheme } from "@x402/evm";
import { privateKeyToAccount } from "viem/accounts";
const account = privateKeyToAccount(process.env.BUYER_KEY as `0x${string}`);
const fetchPaid = wrapFetchWithPaymentFromConfig(fetch, {
  schemes: [{ network: "eip155:5042002", client: new ExactEvmScheme(account) }],   // or "eip155:*"
  // paymentRequirementsSelector: (reqs) => reqs.find(r => BigInt(r.amount) <= 50_000n)  // enforce your own cap
});
const res = await fetchPaid("https://seller.example/report");
```
Both rails in one client: `new CompositeEvmScheme(new BatchEvmScheme(signer), new ExactEvmScheme(signer))` from `@circle-fin/x402-batching/client` (nanopayments.md).

Manual (x402 v1 seller, or custom signer such as Agent Wallet): build EIP-3009 typed data, `circle wallet sign typed-data '<json>' --address 0x… --chain BASE -q`, base64 `{x402Version:1, scheme:"exact", network:"base", payload:{signature, authorization}}` into `X-PAYMENT`. Signature is single-use; re-sign with new nonce on retry.

## Seller side (vanilla + Gateway in one server)

```ts
import express from "express";
import { x402ResourceServer } from "@x402/express";
import { HTTPFacilitatorClient } from "@x402/core/server";
import { BatchFacilitatorClient, GatewayEvmScheme } from "@circle-fin/x402-batching/server";

const server = new x402ResourceServer([
  new HTTPFacilitatorClient({ url: "https://facilitator.example.com" }),   // vanilla onchain rail
  new BatchFacilitatorClient(),                                            // Circle Gateway rail
]);
server.register("eip155:*", new GatewayEvmScheme());   // extends ExactEvmScheme, keeps extra.verifyingContract
await server.initialize();
```
Pointing `HTTPFacilitatorClient` at Circle Facilitator Service: base `https://api.circle.com/v1/facilitator/x402` (client appends `/verify`, `/settle`, `/supported`) with `createAuthHeaders: async () => ({ verify:{Authorization:`Bearer ${KEY}`}, settle:{…}, supported:{} })`. **Inferred from @x402/core types + Circle paths — not shown in Circle docs; verify.** Keyless seller proofs need the raw body hash, which `createAuthHeaders` doesn't receive, so keyless is easiest via direct `fetch` calls as in the quickstart.

Test: `curl -si http://localhost:3000/premium | grep -i payment-required` then decode base64; expect both a vanilla entry and a `GatewayWalletBatched` entry in `accepts`.

Tip from Circle: accept both rails and more than one chain — a buyer can only pay from a chain you accept.
